# ShopFlow Phase 4 — Fixtures and Authentication State: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task (execution method already chosen: inline, then one fresh whole-branch review). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Tests outside `tests/auth/` never see the login page, every spec gets its page objects from fixtures, and the auth suite still starts logged out.

**Architecture:** `fixtures/pages.fixture.js` extends Playwright's `test` with `loginPage` and `inventoryPage`. A `setup` project logs in once and saves `.auth/standard.json`; the `chromium` project depends on it and loads that file. `tests/auth/*.spec.js` opt out with an empty `storageState`.

**Tech Stack:** Playwright 1.64, JavaScript (CommonJS).

**Spec:** `PROJECT_PLAN.md` §5.2 (fixtures), §5.3 (auth state), §5.6 (tagging), §7.1 (config), §8 Phase 4.

**Verified SauceDemo behaviour (recon on 2026-11-01):**

| Question | Observed | Consequence |
|---|---|---|
| What is login state? | One cookie, `session-username=standard_user`, not httpOnly, expiring 600 s after login. localStorage holds only `backtrace-*` keys | The saved state lasts 10 minutes, so it must be regenerated by each run, never committed or reused |
| Reuse the state in a new context | `/inventory.html` loads directly with 6 items | The Phase 4 goal is achievable |
| Logged-in context visits `/` | No redirect; the login form still renders | A login test with no opt-out still passes, which is why the positive spec needs a guard |
| Add to cart, then open a sibling context from the same state | Cart is `cart-contents` in localStorage; the sibling's badge is absent | Each test gets its own copy of the state |
| Log out, then open a sibling context from the same state | Cookie removed only in that context; the sibling stays logged in | AUTH-02 cannot break parallel tests |
| Empty state visits `/inventory.html` | Redirected to `/` with the "You can only access" error | AUTH-08 fails if the opt-out is missing |
| Expired or tampered cookie | Redirected to `/` | Stale state fails loudly rather than passing |

Not tested: whether the cookie's expiry is extended by activity. Assume a fixed 10 minutes.

## Global Constraints

- JavaScript (CommonJS); page objects never contain `expect`; locators only in constructors.
- Specs and the setup file import `test`/`expect` only from `fixtures/pages.fixture.js`. No `new LoginPage`, `new InventoryPage` or `@playwright/test` import under `tests/`.
- Fixtures only for pages that exist today (`loginPage`, `inventoryPage`). Phases 5 and 6 add theirs.
- Config stays Chromium-only until Phase 7, plus the `setup` project. Project definitions match §7.1.
- Every `@smoke` test also carries `@regression` (user decision, 2026-11-01).
- Web-first assertions; no `waitForTimeout`; no `page.getBy…` in specs.
- Branch `phase-4-fixtures`; imperative commits ending `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Read each test run's own exit code (`; echo "exit=$?"`), never a `grep`'s. Use the Edit tool for lines containing regexes.

## Review Focus

1. **Auth tests silently running logged in.** `/` renders the form even when logged in, so AUTH-01, AUTH-02 and AUTH-09 would still pass. Pinned by a no-cookies guard in the positive spec (Task 3 Step 3) and by AUTH-08 in the negative spec (Task 3 Step 2).
2. **Setup saving a logged-out state, or failing quietly.** Setup asserts it reached inventory before saving. With a wrong password, setup must fail, dependants must not run and the exit code must be non-zero (Task 5 Step 2).
3. **Filters dropping the setup project.** `--grep` must not filter out the untagged setup test. Task 5 Step 1 deletes `.auth/` before each filtered run, so a pass proves setup ran.
4. **Missing or stale state.** Running with `--no-deps` and no file must fail, not fall back to a logged-out pass (Task 5 Step 3). A suite running past 10 minutes could outlive the cookie; this is a Phase 7 risk once three browsers run, recorded in Task 5 Step 5.
5. **State leaking between parallel tests.** Logout and cart changes must stay in their own context. Pinned by `--repeat-each=3` (Task 5 Step 4) and by checking the saved file has no `cart-contents` (Task 3 Step 6).
